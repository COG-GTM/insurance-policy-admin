# COBOL characterization harness (AB-520)

Proves that the Java replacement behaves like the COBOL it replaces. The unchanged legacy programs
run under GnuCOBOL against controlled fixtures. Everything they do is stored as golden files, and the
Java implementation must reproduce those files to the cent. The only exceptions are *known
differences* for quirks the business decided to fix, and each one links to that decision.

```
make parity           # both halves below
make parity-check     # harness unit tests, validation, COBOL re-run must equal the golden files (needs cobc)
make parity-java      # Java adapters vs the golden files (pas/pas-parity, JDK 21)
make parity-record    # re-record golden files from COBOL (SUITE=<name> for one suite); review the diff
python3 tools/parity/parity.py run --suite polrnw-renewal --case leap-day-expiry   # print one COBOL run
python3 tools/parity/parity.py precompile UNDWRT   # write the harness source to target/parity/src/
```

GnuCOBOL 3.x is needed for the COBOL half (`apt-get install gnucobol3`, or set `COBC`). CI
(`.github/workflows/parity.yml`) runs both halves on every pull request into `main` and
`devin/ab-516-v3`. `PARITY_SKIP_COBOL=1 make parity-check` validates the data without re-running COBOL
(for machines without GnuCOBOL; CI never sets it).

## Layout

| Path | What it is |
|---|---|
| `suites.json` | Registry: one suite per program scope, with its legacy source, stubs, fixtures, owner ticket and Java adapter (`null` until the capability ticket wires one), plus the fixture tags every run must cover |
| `fixtures/<suite>.json` | Controlled inputs, one case per scenario, with tags and the quirks it exercises |
| `golden/<suite>/<case>.json` | Recorded COBOL behaviour (generated by `make parity-record`, never edited by hand) |
| `known-differences.json` | Allowed Java/COBOL differences, only for quirks with a `fix` decision |
| `cobol/stubs/<PROGRAM>.stubs` | One replacement per `EXEC SQL` / `EXEC CICS` block of the program |
| `cobol/harness/*.cpy` | Harness working storage, SQLCA and helper paragraphs |
| `../tools/parity/parity.py` | Precompiler, runner, recorder and validator (unit tests in `test_parity.py`) |
| `../pas/pas-parity/` | Java side: comparator, known-difference matching, one adapter per wired suite |

## How a COBOL run works

1. **Precompile.** `parity.py` reads `cobol/programs/<PROGRAM>.cbl` (never modified; the legacy trees
   stay byte-for-byte unchanged) and writes a harness copy to `target/parity/src/`:
   - `EXEC SQL INCLUDE SQLCA` becomes `COPY PXSQLCA`. Every other `EXEC` block is replaced by the stub
     with the same ordinal. The stub's fingerprint must match the start of the block text, and the
     stub count must equal the block count, so a changed program fails loudly instead of drifting.
   - `DFHRESP(NORMAL)` becomes `0`, as the CICS translator does.
   - **Decimal-divide emulation.** GnuCOBOL leaves the target unchanged on a division by zero; z/OS
     raises S0CB and CICS abends the task (ASRA) and backs out the unit of work. Before every
     `COMPUTE` that divides by a data item, the precompiler inserts a check that records the abend
     and stops the run.
   - The harness working storage (`PXWORK`) and paragraphs (`PXPROC`) are copied in.
2. **Compile** with `cobc -x -std=ibm` and the copybooks from `cobol/copybooks/`.
3. **Run** each fixture case in a clean environment: input `KEY` becomes `PX_KEY`, cursor rows
   become `PX_R<nnnn>_KEY`, the clock is the case's `run_date` (`COB_CURRENT_DATE`), and files such
   as `PREMRPT` go to a temporary directory.
4. **Observe.** Each stub that writes something (SQL INSERT/UPDATE, CICS SEND/WRITEQ/RETURN) prints
   an *effect*: the operation, the SQLCODE the emulated DB2 returned, and the host variables. Text
   values are right-trimmed, and non-printable bytes are shown as `\xNN`. Numbers keep the scale of
   their COBOL field. *Probes* add internal values that matter for later tickets (the pro-rata factor,
   loss ratio, intermediate premiums).

DB2 emulation in the stubs is deliberately small: reads return fixture values. Any statement can
fail with fixture `SQLCODE_<STATEMENT>` (for example `SQLCODE_SELECT_POLICY: "100"` for not found, or
`SQLCODE_INSERT_PREMIUMS: "-803"` for a duplicate key). DATE columns reject invalid dates with -181,
which is what makes the 29 February renewal (Q-01) fail.

### Stub macros

Stub sections are plain fixed-format COBOL plus these one-line macros:

| Macro | Expands to |
|---|---|
| `@get NAME HOST-VAR` / `@get-num NAME HOST-VAR` | read fixture `PX_NAME` into an alphanumeric / numeric host variable (numbers default to 0) |
| `@sqlcode STATEMENT` | `SQLCODE` = 0, or fixture `SQLCODE_<STATEMENT>` |
| `@db2-date HOST-VAR` | `SQLCODE` = -181 when the value is not a valid YYYYMMDD date |
| `@effect OPERATION` / `@effect-sqlcode` | start an effect / record its SQLCODE |
| `@text NAME HOST-VAR`, `@text-literal NAME VALUE` | text field of the effect |
| `@num NAME HOST-VAR SCALE`, `@num-literal NAME VALUE SCALE` | numeric field of the effect |
| `@probe NAME WS-ITEM SCALE` | internal working-storage value |
| `@row-scope on/off` | fixture names refer to the current cursor row |

## Golden files and comparison

A golden file holds the outcome (`completed` or `abend`, return code, abend code), the effects in
order, the program's `DISPLAY` lines, file artifacts (the PREMBAT report) and the SHA-256 of the
legacy source it was recorded from. `make parity-check` re-runs COBOL and requires byte-identical
output, so golden files cannot be edited by hand or go stale.

`pas-parity` compares a Java adapter's result with the golden file. It checks the outcome, the
effect count and order, each operation and SQLCODE, every text field (exact after right-trim),
every number (decimal compare, so one cent fails), and probes when the adapter reports them. File
artifacts are not compared yet: byte-level report and extract comparison waits for production
samples (FU-13, AB-523/AB-527). `pas/pas-parity/target/parity-report.md` lists what ran, which suites
still lack an adapter and which known differences were used.

## Adding a program or a scenario

1. Add cases to `fixtures/<suite>.json` (or a new suite in `suites.json` with a new stubs file).
   Use synthetic data only (ADR 0001 D9: no production PII in fixtures or golden files).
2. `make parity-record SUITE=<suite>` and review every golden diff against the COBOL source. The
   golden files record *today's* behaviour, defects included.
3. Write the Java adapter in `pas/pas-parity/src/test/java/com/acme/insurance/pas/parity/adapters/`
   (implement `ProgramAdapter`: fixture in, effects out, same names as the stub) and set
   `java_adapter` in `suites.json`. From then on CI fails on any difference.
4. Where the Java deliberately differs, add a known difference (below). Do not re-record golden files
   to make Java pass.

`PrembatRatingAdapter` is the worked example: suite `prembat-rating` runs PREMBAT end to end in COBOL
and `pas-rating`'s `PremiumCalculator` in Java, and all 12 cases match to the cent.

## Known differences

`known-differences.json` entries need: the suite, the cases (or `*`), the result paths that may
differ (`*` for the whole case, or globs like `effects[*].text.DECISION_REASON`), the quirk, the link
to its decision (`docs/modernization/quirk-register.md#q-nn`), the ticket, the reason and `sign_off`.
`make parity-check` rejects an entry whose quirk is not `fix` in the quirk register or whose link is
wrong. While sign-off is `pending` the difference is allowed but listed in the report. Before a
capability goes live (ADR 0001 cutover gate), run with `PARITY_REQUIRE_SIGNOFF=1`: then only entries
with `sign_off: "approved: <who, date, reference>"` count.

The seeded entries (KD-01..KD-05) cover the fixes the register already proposes for suites whose
adapters land in AB-525 and AB-526.

## Fidelity limits

GnuCOBOL with `-std=ibm` is close to Enterprise COBOL for this code (packed-decimal truncation,
unsigned fields, intrinsic date functions), but it is not the production compiler. The mainframe team
has to confirm the following before baselines are frozen (FU-05, FU-13):

- **Uninitialised storage.** GnuCOBOL initialises working storage (spaces, zeros); z/OS depends on
  compile and runtime options. This matters for `WS-ENDORSEMENT-TYPE` (Q-19): the fixtures state the
  assumed storage content explicitly (`STORAGE_WS_ENDORSEMENT_TYPE`). It also matters for
  `WS-PREMIUM-ADJUST` (Q-20), recorded as 0.00. Binary zeros in a packed field would raise S0C7 on
  z/OS.
- **Abends.** Only the decimal-divide case is emulated. Other program checks (S0C7 data exceptions,
  overflow under different `TRUNC` options) are not.
- **CICS and DB2** are reduced to what the programs observe: BMS mapsets are missing from the
  repository (FU-07), so RECEIVE only supplies the policy key and response code. DB2 returns fixture
  values and validates DATE columns only.
- **The PREMBAT report** STRINGs a packed field (Q-29), so its premium bytes are recorded as
  `\xNN` escapes. Comparing it needs a production sample.

## Findings from the characterization runs

- **New quirk Q-520-1:** in UNDWRT and POLRNW, a failed `RECEIVE MAP` does `GO TO 2000-EXIT` out of
  a paragraph PERFORMed without `THRU`, so control falls through the rest of the program. UNDWRT
  writes a decision for an empty record before sending the error, and POLRNW abends on the zero
  premium. Added to the quirk register (proposed decision: fix, pending mainframe verification).
- **Q-15 example:** the register suggests an 11x incurred-to-premium case to show the missing
  surcharge. With 11x the truncated loss ratio is 100.00, which is still above 80, so the surcharge
  applies. The surcharge is only lost when the truncated value is 80.00 or less, for example 10.5x
  (1050% becomes 50.00). Both cases are in the fixtures. The register's parity note should be
  corrected by its owner.
- Confirmed as described in the register: Q-01, Q-02, Q-05, Q-06 (349.9965 becomes 349.99), Q-07,
  Q-14 (credit 850 preferred gives 75, score 1450 shows 450), Q-16, Q-19, Q-20 (adjustment always
  0.00, days after expiry positive, 1096-day term truncated to 96), Q-21, Q-25, Q-28, Q-41.
