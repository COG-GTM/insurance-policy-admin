# PAS quirk register (AB-517)

Every behaviour of the legacy PAS that is surprising, defective, hard-coded or undocumented. Each item has an **owner** and a **preserve / fix** decision.

- **preserve**: the Java replacement reproduces today's behaviour exactly. Parity tests assert it.
- **fix**: the Java replacement deliberately differs. The parity harness (AB-520) records the difference as a *signed-off deviation*, which needs the owner's approval before the capability ticket ships.

**All decisions below are proposals.** No business owner has signed them off in this repository (see [README.md](README.md#sign-off)). Items marked *pending mainframe-team verification* depend on whether the production load modules match the source in this repo ([open-questions.md](open-questions.md), FU-05).

Rules for this register:
- The source of truth is [`quirks.json`](quirks.json). The table and detail sections below are generated by `python3 tools/discovery/pas_inventory.py --write`. `make inventory` fails if they are stale, if a quirk has no owner or decision, or if its evidence no longer matches the cited source.
- AB-517 owns ids `Q-01`..`Q-99`. Other tickets add quirks as `Q-<ticket number>-<n>` (e.g. `Q-526-1`).
- Q-01..Q-04 are the four quirks the ticket already listed. The rest were found during discovery.
- Changing a decision: edit `quirks.json` (`proposed_decision`, `decision_status` such as `approved by <name> <date>`), regenerate, and record the approval in the sign-off table.

### Q-01

**Leap-year renewal date** (POLRNW, defect (known))

The new expiry date is computed as `ADD 10000` to the YYYYMMDD expiry. That is correct for every date except 29 February: 2024-02-29 becomes 20250229, which is not a valid date. DB2 rejects the POLICIES UPDATE (SQLCODE -180/-181). Because of Q-07 the program still attempts the COVERAGES date update, which fails for the same reason so the coverage dates stay unchanged, and then sends the confirmation screen.

- Owner: Product Owner, Policy Administration
- Proposed decision: **fix** (proposed - pending business sign-off)
- Rationale: Epic AB-516 names the leap-year renewal bug as a known defect. The fix needs a product convention for 29 Feb terms (recommendation: expire on 28 Feb of the following year, the same as `LocalDate.plusYears(1)`).
- Parity / characterization note: Characterization tests record today's behaviour for 29 Feb inputs (invalid date / DB2 error) and tag it as a signed-off deviation once the fix is approved. Every other date must match exactly.
- Lands in: AB-526
- Follow-up: FU-01
- Evidence:
  - `cobol/programs/POLRNW.cbl:148`: `ADD 10000 TO POLICY-EXPIRY-DATE`
  - `cobol/programs/POLRNW.cbl:147`: `does not handle leap years properly`

The comment says the business wanted to block renewal when there are more than 3 open claims (JH 2005). Today no renewal is ever blocked for open claims. ### Q-06

**Arithmetic truncates instead of rounding** (PREMBAT, POLRNW, POLEND, UNDWRT, numeric semantics)

No COMPUTE in PAS uses ROUNDED, so intermediate and final results are truncated toward zero into the receiving PIC (V99 for money, V9(06) for the pro-rata factor). Examples: PREMBAT tax = premium * 0.0350 truncated to cents, POLRNW premium * 1.05 truncated to cents.

- Owner: Actuarial / Pricing lead
- Proposed decision: **preserve** (proposed - pending business sign-off)
- Rationale: Changing to HALF_UP would change premiums by a cent on many policies. The epic requires cent-level parity, so use BigDecimal with RoundingMode.DOWN at the same scale as each COBOL receiving field.
- Parity / characterization note: The parity harness compares to the cent. Java code must use BigDecimal with explicit scale + RoundingMode.DOWN wherever COBOL COMPUTE has no ROUNDED.
- Lands in: AB-520, AB-522
- Evidence:
  - `cobol/programs/PREMBAT.cbl:180`: `WS-MOD-PREMIUM * WS-TAX-RATE`
  - `cobol/programs/POLRNW.cbl:127`: `WS-OLD-PREMIUM * 1.05`

### Q-07

**Renewal continues after a failed policy UPDATE** (POLRNW, error handling defect)

If the POLICIES UPDATE fails, 6000-CREATE-RENEWAL-TERM sends the error text, but 0000-MAIN-LOGIC still runs 7000-UPDATE-COVERAGES (moves coverage dates to the new term) and 8000-SEND-CONFIRMATION. - Parity / characterization note: Characterization documents the current partial-update outcome. The Java service is expected to differ (all-or-nothing), so this is a signed-off deviation.

### Q-08

**Generated policy number overflows PIC X(12): last digit dropped, numbers collide** (POLNEW, defect / needs verification)

4000-GENERATE-POLICY-NUM STRINGs 'POL' + WS-POLICY-SEQ (PIC 9(10), zero-padded) into POLICY-NUMBER PIC X(12). That is 13 characters, so the STRING overflows and drops the last digit. POLICY_SEQ starts at 1000000, so sequence values 1000000-1000009 all become 'POL000100000', and 9 of every 10 inserts would hit a duplicate key. The format 'POL' + 9 digits also differs from the 'POL-########' numbers in the facade seed data and API snapshots.

- Owner: Mainframe team (mainframe-ops@acme.com) + Product Owner, Policy Administration
- Proposed decision: **fix** (proposed - pending mainframe-team verification against production load module)
- Rationale: The epic requires existing policy numbers to stay exactly the same. The mainframe team must confirm the production algorithm (the load module may differ from this source) before the Java generator is written. Existing numbers are preserved. Generation of new numbers must not collide.
- Parity / characterization note: Parity tests must assert the production format confirmed by the mainframe team, not this source. Blocked on FU-05.
- Lands in: AB-525
- Follow-up: FU-05
- Evidence:
  - `cobol/programs/POLNEW.cbl:143`: `STRING 'POL' WS-POLICY-SEQ`
